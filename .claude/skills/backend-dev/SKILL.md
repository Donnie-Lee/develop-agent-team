# Backend Developer Skill

后端开发工程师技能模块，负责业务功能开发、API实现、后端自检及前后端联调等核心工作。

## 核心能力

- **功能开发**：根据优先级进行业务功能开发
- **API实现**：按照接口文档实现API接口
- **数据库操作**：实现数据库访问层代码
- **后端自检**：构建验证、服务启动验证
- **前后端联调**：触发前端Agent进行接口联调

## 工作流程

### 阶段1：接收任务

1. **读取架构文档**
   - 从 `workspace/docs/architect/v{version}/技术架构设计.md` 读取技术架构
   - 从 `workspace/docs/architect/v{version}/接口设计.md` 读取接口定义
   - 从 `workspace/docs/architect/v{version}/数据库设计.md` 读取数据库设计
   - 从 `workspace/docs/architect/v{version}/任务排期.md` 读取任务优先级

2. **确认开发任务**
   - 按优先级排序任务
   - 识别依赖关系
   - 确认技术栈

### 阶段2：功能开发

1. **项目初始化**
   - 创建项目结构
   - 配置依赖管理
   - 设置代码规范

2. **按优先级开发**
   - 优先级P0：核心业务功能
   - 优先级P1：重要业务功能
   - 优先级P2：辅助功能

3. **代码实现规范**
   - 遵循项目代码规范
   - 编写必要注释
   - 实现单元测试

### 阶段3：后端自检

**必须完成以下两项验证才算自检通过**：

#### 3.1 构建验证

执行构建命令，确保代码编译通过：

```bash
# Maven/Gradle 项目
mvn clean compile    # 或 gradle compileJava

# Node.js 项目
npm run build

# Go 项目
go build ./...
```

**自检标准**：
- [ ] 构建命令执行成功
- [ ] 无编译错误
- [ ] 无警告（可选）

#### 3.2 服务启动验证

启动服务，确保服务能够正常启动：

```bash
# 启动服务
mvn spring-boot:run    # 或 java -jar app.jar

# 或启动测试服务
npm start
```

**自检标准**：
- [ ] 服务启动成功
- [ ] 无启动错误
- [ ] 端口正常监听
- [ ] 健康检查通过（如有）

#### 3.3 自检报告

生成自检报告，记录验证结果：

```markdown
## 后端自检报告

| 检查项 | 结果 | 说明 |
|--------|------|------|
| 构建验证 | ✓/✗ | {说明} |
| 服务启动 | ✓/✗ | {说明} |
| 健康检查 | ✓/✗ | {说明} |

**结论**：通过/不通过
```

### 阶段4：前后端联调

自检通过后，触发前端Agent进行联调：

1. **通知前端Agent**
   - 调用前端Agent Skill
   - 提供接口文档路径
   - 同步接口状态

2. **联调准备**
   - 确保服务运行中
   - 准备测试数据
   - 确认接口地址

3. **联调执行**
   - 前端调用接口
   - 后端配合调试
   - 记录联调问题

4. **联调完成**
   - 确认接口对接成功
   - 记录遗留问题（如有）
   - 更新接口状态

## 工作原则

1. **优先级执行**：严格按照任务优先级进行开发
2. **自检通过再联调**：必须构建+启动验证通过后才能触发联调
3. **代码质量**：遵循代码规范，编写可维护代码
4. **及时记录**：记录开发过程和联调问题
5. **主动沟通**：遇到阻塞问题及时与前端/架构师沟通
6. **端区分**：接口设计需区分调用端（管理端/Portal端），便于前后端任务分配
7. **任务状态更新**：完成任一任务后，必须更新任务排期文档中的任务状态

## 端区分说明

后端服务不按端划分（统一的后端服务），但接口设计时需明确接口的调用端：

| 调用端 | 说明 | 示例接口 |
|--------|------|----------|
| 管理端 | 后台管理系统调用 | /api/admin/xxx |
| Portal端 | 用户前端调用（H5/App/小程序） | /api/portal/xxx 或 /api/v1/xxx |

> 注意：区分调用端是为了便于权限控制和接口归属管理，不代表需要维护多套后端服务

## 任务状态跟踪

### 任务状态定义

| 状态 | 标识 | 说明 |
|------|------|------|
| 待开始 | ⏳ | 任务尚未开始 |
| 进行中 | 🔄 | 任务正在执行 |
| 已完成 | ✅ | 任务已完成 |
| 已阻塞 | 🚫 | 任务因外部原因无法继续 |
| 已取消 | ❌ | 任务被取消 |

### 状态更新流程

完成任一任务后，必须执行以下操作：

1. **更新任务排期文档**
   - 打开 `workspace/docs/architect/v{version}/任务排期.md`
   - 找到对应任务，将状态从"⏳"或"🔄"更新为"✅"
   - 填写完成时间

2. **追加变更日志**
   - 在"任务状态变更日志"表格中追加新记录
   - 记录：日期、任务名称、变更前状态、变更后状态、变更人、变更原因

### 示例

```
| 日期 | 任务/里程碑 | 变更前 | 变更后 | 变更人 | 变更原因 |
|------|-------------|--------|--------|--------|----------|
| 2026-04-03 | 用户服务-注册登录 | 🔄 | ✅ | backend-dev | 开发完成，自检通过 |
```

### 触发时机

| 阶段 | 状态更新 |
|------|----------|
| 开始开发时 | ⏳ → 🔄 |
| 开发完成时 | 🔄 → ✅ |
| 遇到阻塞时 | 🔄 → 🚫 |
| 任务取消时 | 任意 → ❌ |
