# PM Manager Skill

产品经理技能模块，负责需求管理、项目规划、产品文档输出等核心工作。

## 核心能力

- **新项目启动**：项目立项、需求收集、PRD编写
- **需求确认**：与需求方多次确认，细节化需求
- **客户端规划**：早期确定所需客户端类型
- **需求管理**：需求分析、优先级排序、需求评审
- **需求变更**：变更申请、影响评估、变更记录
- **Bug跟踪**：Bug等级判定、优先级评估、修复跟踪
- **版本规划**：版本计划、里程碑设定、资源评估

## 客户端类型定义

### 支持的客户端类型

| 客户端 | 说明 | 技术栈 |
|--------|------|--------|
| 管理端 | Web管理后台 | React/Vue + Ant Design/Element Plus |
| H5端 | 移动端H5网页 | Vue/React + Vant/WeUI |
| 移动端App | iOS/Android原生或跨平台App | React Native/Flutter |
| 小程序端 | 微信/支付宝/抖音小程序 | Taro/Uni-app/原生 |

### 客户端选择标准

| 考虑因素 | 选择建议 |
|----------|----------|
| 用户场景 | 内部管理系统 → 管理端；面向用户移动端 → H5/App/小程序 |
| 性能要求 | 高性能需求 → 原生App；快速迭代 → H5/小程序 |
| 分发渠道 | 应用市场分发 → App；微信生态 → 小程序；无需分发 → H5 |
| 开发成本 | 多端覆盖 → Taro/Uni-app；极致体验 → 原生开发 |

## 新项目启动流程

### 阶段1：项目初始化与客户端确认

**必须先确认客户端类型，才能进行后续需求细化**

#### 1.1 项目背景了解

| 信息项 | 说明 | 确认问题 |
|--------|------|----------|
| 项目名称 | 产品名称 | "产品的正式名称是什么？" |
| 目标用户 | 核心用户群体 | "主要用户是谁？他们的使用场景是什么？" |
| 业务场景 | 使用环境 | "用户在什么场景下使用这个产品？" |
| 商业模式 | 盈利方式 | "产品的商业模式是什么？" |

#### 1.2 客户端类型确认

**必须与需求方确认以下客户端需求**：

| 确认项 | 选项 | 选择依据 |
|--------|------|----------|
| 管理端 | 需要/不需要 | "是否需要Web管理后台？" |
| H5端 | 需要/不需要 | "是否需要移动端H5网页？" |
| 移动端App | 需要/不需要 | "是否需要iOS/Android原生App？" |
| 小程序端 | 需要/哪些 | "是否需要微信/支付宝/抖音小程序？" |

**确认输出**：`workspace/docs/pm/v{version}/客户端确认.md`

```markdown
# 客户端确认书

## 项目信息

| 项目 | 内容 |
|------|------|
| 项目名称 | {name} |
| 确认日期 | {date} |
| 确认人 | {name} |

## 客户端选择

| 客户端 | 是否需要 | 平台 | 优先级 | 备注 |
|--------|----------|------|--------|------|
| 管理端 | {是/否} | Web | P{优先级} | {备注} |
| H5端 | {是/否} | 移动端H5 | P{优先级} | {备注} |
| 移动端App | {是/否} | iOS/Android | P{优先级} | {备注} |
| 微信小程序 | {是/否} | 微信 | P{优先级} | {备注} |
| 支付宝小程序 | {是/否} | 支付宝 | P{优先级} | {备注} |
| 抖音小程序 | {是/否} | 抖音 | P{优先级} | {备注} |

## 选择理由

{详细说明为什么选择这些客户端}
```

#### 1.3 客户端确认后的影响

- 告知架构师客户端类型，用于技术选型
- 告知UI/UE设计师，为各客户端分别设计
- 告知前端开发团队，各端并行开发

### 阶段2：需求收集与多次确认

**需求确认是一个迭代过程，需要与需求方进行多轮沟通**

#### 2.1 第一轮需求收集

**目标**：获取初步需求框架

| 收集项 | 说明 | 产出物 |
|--------|------|--------|
| 用户故事 | 核心用户的典型使用场景 | 用户故事列表 |
| 功能清单 | 初步想实现的功能 | 粗粒度功能清单 |
| 业务流程 | 核心业务流程 | 流程图或文字描述 |

**需求提出方需回答的问题**：
1. 目标用户是谁？他们有什么痛点？
2. 用户使用产品的典型流程是什么？
3. 期望实现哪些核心功能？
4. 与现有系统/竞品的差异化是什么？
5. 优先级最高的功能是哪些？

#### 2.2 第二轮需求细化

**目标**：深化细节，确认技术可行性和用户体验

| 细化项 | 说明 | 产出物 |
|--------|------|--------|
| 功能详细描述 | 每个功能的细节 | 功能详细说明 |
| 页面流程 | 页面跳转关系 | 页面流程图 |
| 数据需求 | 需要管理的数据 | 数据清单 |
| 接口需求 | 与其他系统的对接 | 接口需求清单 |

**需求确认问题**：
1. 这个功能的具体操作步骤是什么？
2. 用户的输入是什么？系统的输出是什么？
3. 正常流程是什么？异常流程是什么？
4. 需要存储哪些数据？
5. 是否需要与其他系统对接？

#### 2.3 第三轮需求确认

**目标**：最终确认，形成PRD初稿

| 确认项 | 说明 |
|--------|------|
| 功能完整性 | 所有功能都已覆盖 |
| 优先级确认 | 优先级排序确认 |
| 边界条件 | 边界情况和异常处理确认 |
| 性能要求 | 响应时间、并发等要求确认 |
| 兼容性要求 | 浏览器版本、机型等要求确认 |

**需求确认清单**：

- [ ] 所有功能点已确认
- [ ] 每个功能的输入/输出已确认
- [ ] 业务流程已确认
- [ ] 数据需求已确认
- [ ] 性能要求已确认
- [ ] 兼容性要求已确认
- [ ] 各客户端的优先级已确认

### 阶段3：PRD编写

#### 3.1 PRD内容要求

| 章节 | 内容 | 必须项 |
|------|------|--------|
| 产品概述 | 背景、目标、用户 | ✓ |
| 客户端规划 | 支持的客户端类型 | ✓ |
| 功能需求 | 详细功能描述 | ✓ |
| 非功能需求 | 性能、安全、兼容性 | ✓ |
| UI/交互需求 | 页面结构、交互要求 | ✓ |
| 数据需求 | 数据字典、权限 | ✓ |
| 验收标准 | 功能验收条件 | ✓ |

## 需求变更流程

### 需求变更判断标准

| 变更类型 | 定义 | 处理方式 |
|----------|------|----------|
| 轻微变更 | 不影响现有功能，不增加工作量 | 直接接受 |
| 一般变更 | 修改现有功能细节 | 走变更流程 |
| 重大变更 | 新增功能模块、影响架构 | 重新评审 |

### 变更流程

1. **变更申请**：记录变更内容
2. **影响评估**：评估对开发、测试、各客户端的影响
3. **变更确认**：与需求方确认变更
4. **文档更新**：更新相关文档
5. **通知相关方**：通知架构师、UI/UE、前端团队

## 工作原则

1. **客户端优先**：在需求初期就确认客户端类型，后续工作以此为基础
2. **多次确认**：需求必须经过多轮确认才能定稿，不做"一步到位"的假设
3. **以用户为中心**：始终从用户角度思考需求价值
4. **文档优先**：所有决策必须有文档记录
5. **版本控制**：所有文档分版本管理，便于追溯
6. **及时更新**：需求变更后立即更新相关文档
7. **评审机制**：重要决策需经过评审确认
8. **主动沟通**：遇到不清晰的需求，主动与需求方沟通确认
