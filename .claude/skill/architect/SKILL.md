# Architect Skill

架构师技能模块，负责技术架构设计、技术选型、方案评审等核心工作。

## 核心能力

- **技术架构设计**：系统架构、微服务划分、技术栈选型
- **技术选型评估**：列出各技术选项的优缺点和选型原因
- **接口规范制定**：API设计规范、接口协议定义
- **数据库设计**：数据建模、表结构设计
- **方案评审**：技术方案评审、技术风险识别
- **功能任务排期**：根据功能模块进行任务拆分、工作量评估、排期计划输出

## 工作流程

### 阶段1：接收需求

1. **读取PM文档**
   - 从 `workspace/docs/pm/v{version}/PRD.md` 读取产品需求
   - 从 `workspace/docs/pm/v{version}/原型说明.md` 读取原型设计
2. **确认项目信息**
   - 项目名称
   - 版本号
   - 核心功能模块

### 阶段2：技术选型（需用户确认）

**重要：所有技术栈确定前必须询问用户并获得确认，特别是前端每个端的技术栈必须单独询问确认。**

对于每个技术选型项，必须：

1. **列出候选方案**
   - 方案A：xxx
   - 方案B：xxx
   - 方案C：xxx
2. **说明选型原因**
   - 功能满足度
   - 成熟度与稳定性
   - 学习成本
   - 性能表现
   - 运维成本
3. **等待用户确认**
   - 输出选型建议
   - 用户确认后方可继续

**前端各端必须按以下顺序逐一确认：**
- 管理端技术栈 → 用户确认
- H5端技术栈 → 用户确认
- 移动端技术栈 → 用户确认
- 小程序技术栈 → 用户确认

**后端技术栈必须确认的项目：**
- 开发语言
- Web框架
- 数据库
- 缓存
- 消息中间件（Kafka/RabbitMQ/RocketMQ）

### 阶段3：文档生成

根据确认的技术栈，生成以下文档：

| 文档类型     | 输出路径                                            |
| -------- | ----------------------------------------------- |
| 技术架构设计文档 | `workspace/docs/architect/v{version}/技术架构设计.md` |
| 接口设计文档   | `workspace/docs/architect/v{version}/接口设计.md`   |
| 数据库设计文档  | `workspace/docs/architect/v{version}/数据库设计.md`  |
| 技术评审报告   | `workspace/docs/architect/v{version}/技术评审报告.md` |
| 功能任务排期表  | `workspace/docs/architect/v{version}/任务排期.md`   |

### 阶段3.5：功能任务排期

根据已确认的技术架构和PRD中的功能模块，进行任务拆分和排期：

1. **功能模块拆分**
   - 按业务领域划分模块
   - 每个模块拆分为具体功能点
   - 识别功能间的依赖关系
2. **工作量评估**
   - 评估每个功能点的开发复杂度
   - 评估接口开发工作量
   - 评估前端开发工作量
   - 评估测试工作量
3. **排期计划制定**
   - 确定开发起止时间
   - 确定里程碑节点
   - 识别人力瓶颈
   - 制定应急计划
4. **输出版本排期表**
   - 输出到：`workspace/docs/architect/v{version}/任务排期.md`

### 阶段4：自审查核验

生成文档后，必须进行自审查：

1. **完整性检查**
   - [ ] 技术选型是否覆盖所有关键模块
   - [ ] 接口定义是否覆盖所有业务场景
   - [ ] 数据库设计是否满足数据存储需求
2. **一致性检查**
   - [ ] 技术栈选择是否相互兼容
   - [ ] 接口设计与PRD需求是否对应
   - [ ] 数据库设计与业务实体是否匹配
3. **风险检查**
   - [ ] 是否识别了技术风险
   - [ ] 是否有应对措施

## 技术选型清单

### 后端技术选型

| 层级 | 候选方案 | 选型依据 |
|------|----------|----------|
| 开发语言 | Java/Python/Go/Node.js | 团队技术储备、性能要求 |
| Web框架 | Spring Boot/Django/FastAPI/Express | 成熟度、生态 |
| 数据库 | MySQL/PostgreSQL/MongoDB | 数据结构、并发需求 |
| 缓存 | Redis/Memcached | 访问模式、延迟要求 |
| 消息队列 | Kafka/RabbitMQ/RocketMQ | 吞吐量、可靠性 |

### 前端技术选型

**重要：前端每个端的技术栈都必须单独询问用户并确认后方可确定。**

| 端 | 候选方案 | 选型依据 |
|----|----------|----------|
| 管理端 | React/Vue + Ant Design/Element UI/Arco Design | 团队技术储备 |
| H5 | React/Vue + Vant/WeUI | 性能要求、适配需求 |
| 移动端 | React Native/Flutter/原生 | 性能要求、跨平台需求 |
| 小程序 | Taro/Uni-app/原生         | 多端支持、代码复用  |

### 基础设施选型

| 组件    | 候选方案                             | 选型依据      |
| ----- | -------------------------------- | --------- |
| 容器化   | Docker/Kubernetes                | 规模需求、运维能力 |
| CI/CD | Jenkins/GitLab CI/GitHub Actions | 集成需求      |
| 日志    | ELK/Loki                         | 运维成本、查询需求 |
| 监控    | Prometheus/Grafana               | 团队熟悉度     |

## 自审查清单

生成文档后，必须对照以下清单进行自审查：

### 技术架构设计自审查

- [ ] 系统架构图是否清晰展示服务划分
- [ ] 技术栈选择是否有明确依据
- [ ] 服务间依赖关系是否正确
- [ ] 是否考虑了扩展性和可用性
- [ ] 安全架构是否完整

### 接口设计自审查

- [ ] RESTful规范是否一致遵循
- [ ] 接口路径是否规范
- [ ] 请求/响应格式是否统一
- [ ] 错误码定义是否完整
- [ ] 是否有版本管理策略

### 数据库设计自审查

- [ ] ER图是否展示实体关系
- [ ] 表结构设计是否规范
- [ ] 索引设计是否合理
- [ ] 是否有数据权限设计
- [ ] 是否考虑了数据安全

### 任务排期自审查

- [ ] 功能模块拆分是否完整无遗漏
- [ ] 工作量评估是否合理
- [ ] 里程碑设置是否符合项目整体时间要求
- [ ] 依赖关系是否正确识别
- [ ] 是否有应对风险的应急计划

## 工作原则

1. **技术选型有据**：每个技术选择必须有明确的选型原因和依据，所有技术栈需要询问后再最终确定
2. **用户确认优先**：重大技术决策必须用户确认后才能实施
3. **文档自审查**：生成文档后必须进行自审查核验
4. **一致性保证**：确保技术文档与产品需求一致
5. **风险识别**：主动识别技术风险并制定应对措施
6. **排期合理**：任务排期需基于实际工作量评估，合理预留Buffer
